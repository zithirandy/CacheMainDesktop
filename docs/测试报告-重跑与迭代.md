### 0.0v 第十轮：补上"连接失败"这条从未覆盖的路径，矩阵增至 17 项

审视覆盖矩阵时发现一个刺眼的空白：**所有套件都只断言连接"成功"**。
`check-live-servers.mjs` 甚至专门断言页面里**不出现** `Connection refused` ——
也就是说**失败路径从来没有被测试过**。

而这恰恰是用户最容易遇到的状态：刚添加服务器时填错主机、密码写错、服务没启动。

**新增 `scripts/check-connection-errors.mjs`**，用独立后端喂入 3 个**刻意坏掉**的连接
（全部指向 loopback，按安全规则不碰任何真实/生产库）：

| 连接 | 故障 |
|---|---|
| Dead Redis | `127.0.0.1:6399`（无监听） |
| Wrong Password Redis | `127.0.0.1:6379` + 错误密码 |
| Dead Memcached | `127.0.0.1:11399`（无监听） |

对 7 条路由（两个面板的 dashboard / keys，以及 analysis）断言三件事：

1. **HTTP 2xx** —— 不崩；
2. **页面中不出现任何 PHP 诊断信息**（`Fatal error` / `Warning:` / `Stack trace` / `Uncaught` …）——
   不把内部错误泄给用户；
3. **后端经历全部失败后仍在服务**，且**没有因失败请求泄漏 php 进程**。

**结果：16 项断言全部通过。** 结论是正向的 —— 坏连接不会让应用崩溃或吐出 PHP 错误。

**同时做了反向验证**（这点很重要）：把"无 PHP 错误"这条断言**改造成强制失败**后运行，
得到 `exit=1`、`FAIL lines=7`。即**这条断言确实会红**，绿是有意义的 ——
本仓库已出现过两个"任何错误都 exit 0"的假通过套件（P2），新增测试必须自证不是同类。

顺带处理了 `fetch` 退出阶段的 undici 拆卸断言（`assert(!this.paused)`）：
仅在收尾阶段、且仅这一种断言被忽略，其它异常照旧 `exit 1`。
（该断言在本会话多次出现于其它脚本尾部，是 Node 内置 fetch 的已知行为，非应用问题。）

**矩阵由 16 项增至 17 项，全绿。**

### 0.0w 第九轮：把 P8 从"测试修复"提升为"产品修复"，并如实记录其边界

第八轮把 `ELECTRON_RUN_AS_NODE` 只当测试问题修掉了（在测试脚本里删掉该变量）。
本轮追问：**如果真实用户环境里存在这个变量，应用会怎么表现？** 实测结果很难看：

| 启动方式 | 现象 |
|---|---|
| `CacheMainDesktop.exe`（带该变量） | **静默退出，无任何输出** |
| 带 `--remote-debugging-port=19450` | `bad option: --remote-debugging-port=19450` |

即**一个桌面应用在配置不对时什么都不说就退出** —— 最糟的失败形态。
而该变量由 VS Code 扩展宿主、部分 npm/Electron 构建链路、DSH 宿主等**父进程**注入，
用户可能完全无辜。

**修复：新增 `bootstrap.cjs` 作为入口**（`package.json` 的 `main` 指向它），
先判断"是否真由 Electron 托管"，不是就打印带排查步骤的提示并 `exit 1`。

**为什么必须是 CJS 入口**：ESM 的 import 会被提升、在模块体之前求值，
所以 `main.mjs` 里的任何检查都来不及 —— `import {app} from 'electron'` 会先抛错。
CJS 入口最先执行，是唯一能可靠报错的位置。

**本轮我又犯了一次"凭假设"的错**：最初用 `process.versions.electron` 判断，
第一次真实运行就被推翻 —— 该值在 `ELECTRON_RUN_AS_NODE` 下**仍是 `44.4.5`**：

```
ELECTRON_RUN_AS_NODE = 1
versions.electron    = 44.4.5     ← 我假设是 undefined，错了
process.type          = (unset)    ← 真正的判据
```

改用 `process.type` 后，开发模式实测给出清晰提示并 `exit 1`，正常启动不受影响。

**两个必须同时改的地方**：`electron-builder.yml` 与 `scripts/electron-builder.offline.mjs`
的 `files` 都要加 `bootstrap.cjs`；漏掉则 `main` 指向 asar 里不存在的文件，**打包版直接起不来**。
已用 asar 解析确认产物含 `bootstrap.cjs` 且 `main = bootstrap.cjs`。

**如实记录一处边界（未解决）**：**打包版带该变量时仍静默退出，且连 bootstrap 都没执行**。
证据：在 `bootstrap.cjs` 顶部临时加文件写入标记 —— 正常启动时标记出现（`type=browser`），
带该变量时**标记为空**，说明打包版在加载任何 JS 之前就已退出。
故该模式下**不可能**打印任何自定义信息（不是判断逻辑没生效）。
开发模式（`npm start` / `npx electron .`）能正常给出提示。

**回归验证**：入口由 `main.mjs` 改为 `bootstrap.cjs` 是结构性改动，
重新打包后窗口正常、**全量矩阵 16/16 全绿**，确认无副作用。

### 0.0z 第八轮：定位并修复两个"只在全量套件里失败"的假阳性（P8）

第七轮新增连接管理窗口测试后，出现两个**只在 `npm run verify` 全量运行时失败、单独运行必过**的套件：

- `connections-window`：`app exited early with code 9`（3 次重试全失败）
- `check-plan`：间歇性 `FAIL memcached: no fake 0.00B sizes`

我最初按"顺序依赖/资源竞争"方向猜了很多（单实例锁、残留 `php.exe` 锁 DLL、端口占用），
**全部被实验否定**：手工用不同 `--user-data-dir` 启第二个实例完全正常；前后进程数均为 8/2、无残留。

**决定性实验（只改一个因子）**：同一机器、同一时刻、仅改运行方式：

| 运行方式 | 结果 |
|---|---|
| `node scripts/check-connections-window.mjs` | ✅ 通过（此前 5/5） |
| `npm run verify -- --only connections-window` | ❌ **100% 失败**，每次 `exit code 9` |

再对比两种环境的变量，找到唯一可疑项：

```
ELECTRON_RUN_AS_NODE = "1"     ← 两种方式都存在（由 DSH 宿主注入）
```

**根因（A/B 证明）**：`ELECTRON_RUN_AS_NODE=1` 会让 Electron 可执行文件**退化成纯 Node** ——
不加载开窗口的主脚本、不输出日志、直接退出。用**完全相同的参数**只切换该变量：

| 条件 | 结果 |
|---|---|
| 保留 `ELECTRON_RUN_AS_NODE=1` | ❌ 立即退出，stderr **完全为空** |
| 删除该变量 | ✅ 启动成功，后端 `ready`，页面正常 |

`exit code 9` 与"stderr 为空"由此解释：进程在 Electron 初始化前就走了 Node 路径。

**修复**：`scripts/check-connections-window.mjs` 新增 `electronEnv()`，
spawn 打包应用前 `delete env.ELECTRON_RUN_AS_NODE`，用于所有启动尝试。
已核查全部脚本：**只有这一个**会 spawn 打包应用（其余两处引用只是注释/路径常量）。

**为什么 `check-plan` 也跟着好了**：它同样在 npm 环境下经 `PhpBackend` 启动子进程。
修复后连续 **3 轮全量运行均 16/16**，`check-plan` 未再复现 ——
此前那个 "0.00B" 偶发失败与本次是**同一环境根因**，并非 Memcached 渲染缺陷。
这也解释了我为何静态检查两条渲染路径都找不到问题。

**方法论教训**：我先前把"单独过、全量挂"直接归因为顺序依赖，并据此尝试修复 ——
都属于**没有根因就改**。真正有效的是**固定其他变量、只切换"运行方式"**这一个因子，
差异立刻收敛到一个环境变量。另外第七轮加的 stderr 输出在此起了关键作用：
**stderr 完全为空**本身就是"根本没走到应用代码"的强证据。

### 0.0x 第六轮：把 15 条测试命令收敛成一条（`npm run verify`）

- 应用未运行时，依赖端口的套件标记为 **SKIP 而非假通过**；

**已验证的行为**（不只是"能跑通"）：

最后一项是特意加的：**"过滤条件没匹配到任何东西"看起来像绿灯**，正是本仓库已栽过两次的

### 0.0a 第五轮：验证"解压即用"，并发现 P7（Windows 8.3 短路径导致 PHP 无法启动）

前几轮都在 `dist/win-unpacked/` 原地验证。但本应用的卖点是**"零安装：自带 PHP，解压即用"**，
所以真正该验的是**把 zip 解压到别处再运行**。本轮做了，**结果第一次是失败的**。

**现象**：解压到 `%TEMP%\pca-portable-test` 后启动，窗口标题为 **`Error`**，后端完全起不来：

```
PHP:  syntax error, unexpected '~' in Unknown on line 1
Fatal Error opcache.file_cache must be a full path of an accessible directory
```

**根因（受控 A/B）**：`%TEMP%` 展开后是 **8.3 短路径** `C:\Users\ADMINI~1\...`。
短路径含 `~`，而 **PHP 的 ini 解析器无法处理这个字符** —— `-d` 传参直接语法错误，
`opcache.file_cache` 因此没被正确设置，PHP 拒绝启动。

对**同一个目录**的两种写法实测：

| 传入的路径形式 | 结果 |
|---|---|
| `C:\Users\ADMINI~1\AppData\Local\Temp\pca-portable-test` | ❌ `syntax error, unexpected '~'` |
| `C:\Users\Administrator\AppData\Local\Temp\pca-portable-test` | ✅ 正常启动 |

**影响面**：任何安装路径含"长组件名"的用户都可能踩到（短路径由 Windows 自动生成，用户无感），
表现为**应用启动即失败、原因难以理解**。这正是"打包版可用性"的关键一环。

**修复**：`lib/backend.js` 新增 `#longPath()`，用 `realpathSync.native()` 把 8.3 短路径展开为长路径，
并应用于 `phpExe`、`docroot` 与 `-d opcache.file_cache=` 的值。
（实测 `realpathSync.native(short)` 与 `realpathSync(long)` 结果一致。）

**验证**：重新打包 → 重新解压到**同一短路径位置** → 启动成功，后端命令行已无 `~1`：

```
...\pca-portable-test\resources\php\php.exe
  -d opcache.file_cache=C:\Users\Administrator\...\resources\php\tmp\opcache
  -d opcache.file_cache_fallback=1 -S 127.0.0.1:56947 -t ...\webapp
```

**并且对解压出的副本跑完整矩阵：15/15 全绿。**

**方法论教训**：我先前只 grep 源码里有没有硬编码绝对路径，就判断"可移植性没问题" —— 这**不够**。
绝对路径字面量是一类问题，**路径的书写形式**（短/长、UNC）是另一类，只有真正换位置运行才会暴露。

#### P6（严重回归，我引入的）：相对路径 opcache.file_cache 让打包版 PHP 完全无法启动

**背景**：第一轮为修 P1（PHP 因 ASLR 间歇启动失败），我在 `fetch-php.mjs` 的 php.ini 模板里加了
错误信息提示的两个指令，其中 `opcache.file_cache` 写成了**相对路径** `"tmp/opcache"`。

**后果**：全新打包的 PHP 直接拒绝启动：

```
Fatal Error opcache.file_cache must be a full path of an accessible directory
```

即**按第一轮的做法重新打包，会产出一个根本起不来的应用**。当时没暴露，是因为 `dist/` 里那份
php.ini 是旧构建产物（不含该指令），应用一直正常。

**实测**（`scripts/probe-opcache-aslr.mjs`，每种配置 12 次启动）：

| 配置 | 成功率 | ASLR 失败 |
|---|---|---|
| opcache 开，无 file_cache 指令 | **0/12** | 12 |
| opcache 开 + 仅 `file_cache_fallback=1` | **0/12** | 12 |
| opcache 开 + **绝对路径** file_cache + fallback | **12/12** | 0 |
| opcache 完全关闭 | **12/12** | 0 |

两条关键结论：

1. **只加 `file_cache_fallback` 没用**。错误信息让"配置这两个指令"，但真正起作用的是
   `opcache.file_cache`。我此前"3/3 启动成功"的判断是**运气** —— 少数次成功证明不了什么。
2. **相对路径会让 PHP 拒绝启动**，必须绝对路径（且目录须存在）。

**最终修复**（两处，各解决一个约束）：

- `lib/backend.js`：新增 `#opcacheArgs()`，在 **spawn 时**用 `-d` 传
  `opcache.file_cache=<绝对路径>` + `opcache.file_cache_fallback=1`。
  打包版无法在 php.ini 写死路径（安装位置未知），但**启动进程知道 php.exe 在哪**，可运行时算出绝对路径。
  实测 `PhpBackend` 连续启动 **12/12**；打包版后端命令行确认含 `-d opcache.file_cache=...`。
- `scripts/fetch-php.mjs`：模板改为 `phpIni(phpDir)` 函数写入**绝对**路径，并预建 `tmp/opcache`
  （绝对路径若目录不存在同样失败）。测试用根目录运行时据此重新生成，直接启动 **6/6**。

## 3. 本轮修复的问题

### P1 — 根目录 PHP 因 ASLR 无法启动（阻断型，环境问题）

**现象**：`php/php.exe` 每次启动即 `Fatal Error Opcode handlers are unusable due to
ASLR. Please setup opcache.file_cache and opcache.file_cache_fallback directives`，
进程立刻退出。**阻断了 `smoke` 与 `check-ini-path`。**

**排查**：根目录与 `resources/php/` 的 `php.exe`、`php8.dll` **SHA256 完全相同**，
`php.ini` 也逐字相同，但根目录版本 3/3 必失败、打包版本 2/2 必成功。属 ASLR 地址布局差异被固化。

**修复**：按错误提示本身给出的方案，在 `fetch-php.mjs` 的 `PHP_INI` 模板中加入
```ini
opcache.file_cache="tmp/opcache"
opcache.file_cache_fallback=1
```
并同步到根目录 php.ini。修复后根目录 `php -S` **3/3 正常启动**，`smoke` 与 `check-ini-path` 均恢复。

### P2 — `check-ini-path.mjs` / `check-layout.mjs` 是"假通过"测试（测试设计缺陷）

**现象**：两个脚本都写着 `process.on('uncaughtException', () => process.exit(0))`。
后端**完全无法启动**时它们静默退出 0 —— 也就是说，P1 那种"PHP 根本跑不起来"的状态，
在这两个测试里**一直显示为通过**。

**修复**：改为记录错误并以 1 退出（与 `check-plan`/`check-sticky`/`check-contrast` 的既有正确写法一致）。
**验证**：把路径临时指向不存在的 `php.exe`，脚本现在**正确 exit 1** 并打印原因；恢复后 exit 0。

### P3 — `check-plan.mjs` 的 Memcached 断言依赖环境状态（脆弱断言）

**现象**：`check('memcached: shows Never for never-accessed keys', mcPage.includes('Never'))` 失败。

**根因**（已实测）：该断言要求页面上出现 "Never"，而这**只在键的 `la`（最后访问）为 0 时**才成立。
测试用的 fixture 键是在检查前几秒写入的，其 `la` 为新鲜时间戳，因此渲染为 "2 minutes ago"。
断言能否通过取决于 seed 与检查之间的时序，属**设计上不可靠**，不是功能缺陷。

`Format::timeDiff(0)` → `'Never'` 已直接单测确认正确；"57 years ago" 的原始回归由相邻断言覆盖。

**修复**：断言改为检查 Last used 列**确实被格式化**（"Never" 或 `N unit(s) ago` / "less than a minute"），
这才是这一列真正会回归的点（原始 epoch 泄漏）。修复后 `check-plan` 全部通过。

### P4 — **新发现**：大值不换行，把页面撑到 734,407px 宽（功能缺陷）

这是本轮最重要的新发现，比原报告的 O9 严重得多。

**现象**：100KB 的**无空格字符串**（hash、base64、压缩 JSON 的典型形态）在键详情页里
**不换行**，实测容器 `clientWidth = 734,407px`、`horizontalScroll = false` —— 即内容把盒子
（和整个页面）横向撑到 73 万像素，而不是在盒内滚动。原先报告的 O9 只说"页面变长"，
实际是**页面变宽到不可用**。

**根因**：`partials/view_key.twig` 的值容器只有 `overflow-auto`，没有任何换行约束；
`overflow-auto` 单独并不能约束 inline 内容的横向尺寸。同一文件第 2 行的键名**早就用了 `break-all`**，
值容器却漏了。

**修复**：值容器加 `break-all`（沿用项目既有写法），与 `max-h-96` 一起生效。

**验证**（`check-big-value-collapse.mjs`，修复前后对比）：

| | 修复前 | 修复后 |
|---|---|---|
| `clientWidth` | **734,407px** | **738px** |
| `scrollWidth` | 734,407px | 738px |
| `clientHeight` | 56px | 384px（受 `max-h-96` 限制） |
| `scrollHeight` | 56px | 25,040px（盒内纵向滚动） |
| 横向溢出 | 是（撑爆页面） | 否 |

### P5 — `check-live-servers.mjs` 依赖已过期数据（脆弱测试）

**现象**：`FAIL memcached shows seeded key "session:abc"`。

**根因**：该检查依赖 `scripts/test-memcached-seed.py` 事先灌入的数据，而其中一个键
带了 `600s` TTL；只要检查在 10 分钟后运行就必然失败，**与代码好坏无关**。

**修复**：脚本内置自灌数据（Redis 6 键、Memcached 4 键，**全部不设 TTL**），
不再依赖外部 seed 步骤，也不再会随时间腐坏。修复后 16/16 通过。

## 4. ⚠️ 撤回一项此前结论：D5（窗口几何）**无法复现**

我在 2026-10-06 的修复报告中把 D5 记为"严重缺陷：窗口状态在 DPI 缩放下被错误还原，
主内容区被压到 339px"，并据此新增了 `correctionForUsableContent()`。
**本轮用实测数据重新检验后，该结论不成立，我在此撤回。**

用应用真实的 `BrowserWindow` 参数（`minWidth: 900`）实测"请求宽度 → 实际视口 → 内容区"：

```
requested   getBounds    viewport      mainContent  ratio   verdict
600         900          887x805       647          1.015   usable
700         900          887x805       647          1.015   usable
900         900          887x805       647          1.015   usable
1000        1000         987x805       747          1.013   usable
1280        1280         1267x805      1027         1.010   usable
1289        1289         1276x805      1036         1.010   usable
1440        1440         1427x805      1187         1.009   usable
1600        1440         1427x805      1187         1.009   usable
2000        1440         1427x805      1187         1.009   usable
```

三条结论：

1. **bounds 与视口单位一致**（比值恒为 ~1.01），我原先"DPI 单位换算错乱"的假设**是错的**。
2. **`minWidth: 900` 有效**：请求 600 也被抬到 900，内容区**任何情况下都 ≥647px**，不存在 339px 的可用状态。
3. 保存宽度 **1289 实测得到 1276 的视口**，而不是我记录的 607。我**无法用应用当前的窗口配置复现 607**。

**因此 D5 从"已修复的严重缺陷"改记为"未复现的偶发观察"**。

**遗留问题（已用实测数据定论，见 §0.1）**：`correctionForUsableContent()` 的触发条件是视口 < 840px，
而应用真实的 `BrowserWindow` 配置（`minWidth: 900`）在**全部 6 种几何场景**下都给出 ≥887px 的视口
—— 该函数在当前配置下**不可达**。它的 6 项单测验证的是"给定输入下的行为"，
但**这些输入应用本身产生不出来**（且已实测确认产生不出来）。

**我的处理**：**保留**该函数，因为它是无害的防御代码 —— 若 `minWidth` 未来被调小、
或运行环境的窗口行为变化，它能兜住。但它在今天**不修复任何可复现的问题**，
因此在本报告中如实标注，而非当作已完成的功能修复。
是否保留、还是连同 6 项单测一起删除，属产品取舍，请维护者决定；我未擅自删除。

## 7. 结论

- **测试矩阵 14/14 通过**，含真实 Redis/Memcached 上的 16 项浏览器端到端断言，
  以及 19 个面板/标签页的零错误扫描。
- 修复了 1 项**真实功能缺陷**（P4：大值不换行导致页面横向撑爆至 73 万像素）
  与 4 项测试/环境问题，其中 P1（PHP 完全无法启动）此前被两个"假通过"测试掩盖（P2）。
- **清除了全部静默通过型测试**：审计 16 个脚本，现在没有任何脚本会在失败时 exit 0（§0.2）。
- **撤回了 1 项此前的错误结论**（D5），并用 6 个场景实测证明相关函数当前**不可达**（§0.1），
  作为明确的待决策项留给维护者，而非伪装成已完成的修复。
- **第二轮迭代未再发现新的功能缺陷**：19 个面板/标签页、全部 CRUD 路径、真实缓存服务端到端
  均为干净。剩余的不确定来源只有 §4 的待决策项与 §5 的未验证项（打包、多显示器）。

### 关于"迭代到没有问题为止"

本目标可以无限延伸（例如压测、多显示器、故障恢复、Electron 版本升级后的行为），
因此无法声明"绝对没有问题"。基于可复现证据的当前状态是：**已知功能缺陷为 0**；
测试矩阵全绿；未覆盖的边界已在 §5 逐条列出。
若需继续，建议的方向是 §5 中的"多显示器/热插拔"与"打包后验证"，但两者都需要
当前环境中不存在的外部条件（第二块显示器、完整的 `npm run dist` 耗时预算）。
